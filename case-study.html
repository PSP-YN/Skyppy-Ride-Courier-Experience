04 · USERS & JOBS

Five role-specific needs

Rider

Correct pickup, predictable fare, suitable vehicle, driver details, safety and easy cancellation.

Driver partner

Request details and payout before accepting, fair decline, pickup navigation, verification and earnings.

Sender

Package type, weight, value, handling, pickup schedule, transparent cost and shipment events.

Receiver

Delivery window, sender context, safe handover, private verification and problem reporting.

SMB operator

Bulk shipment overview, exception queue, quick actions and exportable records.

Shared constraints

Low-end Android, interrupted data, regional language, accessibility, shared phones and first-time use.

07 · ACCESSIBILITY & WEAK NETWORK

Built for imperfect conditions

  • Semantic landmarks, labelled controls, keyboard access and visible focus.
  • Reduced-motion preference; status is never communicated by colour alone.
  • Large touch targets, plain language and explicit next actions.
  • Core ride and courier fields use side-by-side English/Kannada labels; the language toggle changes selected hero/title copy only. This is partial localization, not a complete translation. Production copy needs native-speaker review and layout QA.
  • Low-data mode visibly indicates reduced motion; no backend sync is claimed.
  • Production must preserve drafts securely, show last successful sync, queue safe retryable operations and prevent duplicate booking/payment with idempotency.
  • Safety escalation, masked calling, consent-based location sharing and emergency response need staffed operational ownership.
08 · WHAT WORKS / WHAT IS SIMULATED

Prototype scope honesty

Interactive in this prototype

  • Ride type selection and itemized sample fare.
  • Matching, trip, payment and rating states.
  • Driver accept/decline and stage progression.
  • Courier package estimate, timeline and exception.
  • Receiver demo PIN.
  • SMB filtering, add sample row and CSV export.
  • Responsive layout and low-data / language toggles.

Not connected to production

  • No Skyppy API, authentication, database or persistent booking.
  • No real driver dispatch, GPS, map tiles, route/ETA or push alerts.
  • No payment, wallet, refund or live tariff engine.
  • No courier partner network, OTP service or proof storage.
  • No field user testing or Kannada linguistic validation completed.
  • No verified service coverage, SLA, insurance or restricted-goods policy.

All prices, locations, driver identities, PINs, tracking references and dashboard rows are fictional demo content. Do not use this concept to book a ride or send a parcel.

11 · NEXT VALIDATION

Before a production launch

  1. Moderated usability tests with riders, driver partners, senders, receivers and SMB operators in Mysuru.
  2. Validate Kannada copy with native speakers; test low-end Android and interrupted mobile data.
  3. Confirm Skyppy's actual fare rules, service areas, courier SLAs, restricted items and support escalation.
  4. Integrate approved APIs with auth, roles, audit logs, idempotent transactions and secure proof-of-delivery storage.
  5. Test driver no-show, cancellation, pickup delay, wrong address, payment failure, recipient unavailable, damaged parcel and disputed delivery.
  6. Replace provisional palette/logo only after brand assets are approved; rerun accessibility and contrast checks.
